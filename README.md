# Inkwell — совместный редактор документов

Веб-редактор документов в духе Google Docs: real-time совместное редактирование,
офлайн-режим с корректным слиянием правок и авторский дизайн («письменный стол /
чернильница» — тёплая бумага, чернильный текст, морская волна и состаренная латунь
в качестве акцентов).

```
docs-clone/
├── server/   REST API + WebSocket-синхронизация + SQLite-персистентность
└── client/   React + Vite + Tiptap + Yjs
```

## Запуск

Понадобятся два терминала — сервер и клиент запускаются отдельно.

### 1. Сервер

Требуется **Node.js 22.5+** (используется встроенный модуль `node:sqlite` —
никаких нативных зависимостей и компиляции при установке, поэтому `npm install`
работает одинаково на Windows/macOS/Linux без Visual Studio Build Tools/Xcode
Command Line Tools).

```bash
cd server
npm install
npm start          # http://localhost:4000
```

При первом запуске автоматически создаётся `server/data/inkwell.sqlite3`
(база в git не хранится).

### 2. Клиент

```bash
cd client
cp .env.example .env   # при необходимости поменяйте VITE_API_URL
npm install
npm run dev             # http://localhost:5173
```

Откройте `http://localhost:5173` в двух разных вкладках/браузерах (или дайте
ссылку соавтору в локальной сети через `http://<ваш-IP>:5173`, предварительно
запустив клиент с `npm run dev -- --host`) — оба увидите правки друг друга
в реальном времени.

### Проверка офлайн-сценария

1. Откройте документ, начните печатать.
2. В devtools браузера включите Network → Offline (или отключите Wi-Fi).
   Индикатор в шапке переключится на «Офлайн — правки сохраняются локально».
3. Продолжайте редактировать — все изменения пишутся в IndexedDB браузера.
4. Включите сеть обратно. Индикатор пройдёт через «Синхронизация…» и вернётся
   к «В сети — изменения сохранены»; правки, сделанные оффлайн (в том числе
   и другим человеком в этот же момент в другой вкладке), сольются без потерь.

## Архитектура

### Почему Yjs, а не Automerge/ShareDB

- **CRDT, а не OT** — не нужен центральный сервер-арбитр с транзакционным
  порядком операций; клиенты могут расходиться сколь угодно долго (в том
  числе полностью офлайн) и детерминированно сойтись при следующей встрече.
  Это прямое требование ТЗ («офлайн + корректный merge»).
- **y-prosemirror / Tiptap-интеграция из коробки** — `@tiptap/extension-collaboration`
  и `@tiptap/extension-collaboration-caret` официально поддерживаются
  командой Tiptap и избавляют от самостоятельной синхронизации позиций курсора
  с изменяющимся деревом документа (самая частая причина багов в таких
  задачах).
- **y-indexeddb** даёт офлайн-хранилище «из коробки»: каждая правка пишется
  в IndexedDB синхронно с применением к CRDT, до всякой сети — то есть
  оффлайн-режим не «эмулируется», а является основным путём данных.
- **Automerge** решает ту же задачу, но экосистема редакторов (Tiptap/ProseMirror,
  курсоры соавторов, IndexedDB-провайдер) для него менее зрелая на практике.
  **ShareDB** — это OT, а не CRDT: офлайн-слияние там сложнее и требует
  собственной логики транформации операций после долгого разрыва соединения,
  что как раз то, чего просит избежать ТЗ.

### Почему свой WebSocket-протокол, а не пакет `y-websocket` целиком

Начиная с версии 3.x пакет `y-websocket` поставляет только клиентскую часть —
серверная реализация вынесена в отдельные (менее сопровождаемые) пакеты.
Протокол синхронизации (`y-protocols/sync`) и presence-протокол
(`y-protocols/awareness`) — это чистые, хорошо документированные примитивы
кодирования/декодирования; реализовать поверх них комнату на `ws` — около
150 строк, зато даёт полный контроль над персистентностью (см. ниже) и
понятную точку для расширения (аутентификация, права доступа, лимиты).
Клиент использует официальный `y-websocket` (`WebsocketProvider`) — протокол
на обеих сторонах идентичен.

### Персистентность (SQLite)

Схема из трёх таблиц (`server/src/db/database.js`):

- `documents` — только метаданные (заголовок, время создания/обновления) для
  списка документов.
- `doc_updates` — **append-only** журнал всех инкрементальных Yjs-апдейтов.
  Каждая правка от любого клиента синхронно дописывается сюда ещё до того,
  как её можно будет считать «сохранённой» — это и есть источник надёжности
  при внезапном падении процесса.
- `doc_snapshots` — сжатое состояние CRDT. Когда лог апдейтов одного документа
  превышает порог (150 записей) или комната закрывается (последний клиент
  отключился), все апдейты сливаются в новый снапшот, а лог очищается —
  чтобы время открытия документа не росло с историей правок.

При открытии документа сервер восстанавливает Y.Doc как
`применить снапшот → применить все апдейты из лога поверх` — то есть
повторяет ту же модель «snapshot + WAL», что используется в реальных базах
данных.

### Совместное редактирование и присутствие

- Одна комната (`server/src/ws/rooms.js`) = один `Y.Doc` в памяти сервера на
  документ, общий для всех подключённых сокетов. Каждое соединение обменивается
  с комнатой стандартным рукопожатием sync-протокола (`SyncStep1` → `SyncStep2`),
  после чего получает и рассылает только дельты.
- Presence (кто в документе, цвет, курсор/выделение) — отдельный
  awareness-канал того же WebSocket-соединения; при разрыве соединения
  курсор конкретного участника гарантированно удаляется (`removeAwarenessStates`),
  а не «зависает» в документе.
- Заголовок документа хранится не только в SQLite, но и в самом `Y.Doc`
  (`ydoc.getMap('meta')`) — это значит, что переименование тоже синхронизируется
  в реальном времени и корректно работает офлайн, а не только тело документа.

## Стек

| Слой | Технология | Зачем |
|---|---|---|
| Редактор | Tiptap 3 (ProseMirror) | зрелая схема документа, готовая интеграция с Yjs |
| Синхронизация | Yjs + y-protocols (sync, awareness) | CRDT, конфликтов не существует по конструкции |
| Офлайн | y-indexeddb | локальное хранилище как основной путь записи |
| Транспорт | `ws` (сервер) + `y-websocket` (клиент) | тонкий, предсказуемый протокол поверх обычного WebSocket |
| Хранилище | SQLite через встроенный `node:sqlite` | не требует нативной компиляции (в отличие от `better-sqlite3`), доступен «из коробки» в Node 22.5+ — установка не зависит от наличия C++ toolchain на машине |
| API | Express | минимальный REST для списка/CRUD документов |
| Frontend | React + Vite | быстрый dev-цикл, самый частый выбор для SPA такого рода |

## Дизайн-система

Токены — в `client/src/styles/tokens.css`. Тема сознательно уходит от
типичных «AI-дефолтов» (кремовый+терракота, скруглённые SaaS-карточки,
Tailwind-палитра из коробки):

- **Бумага** (`--paper`, `--paper-raised`) — тёплый, слегка ludovico-серый
  оттенок, а не чистый белый и не классический кремовый.
- **Чернила** (`--ink`) — текст и основная графика: тёмно-синий, почти
  чёрный, как настоящие чернила, а не нейтральный `#111`.
- **Морская волна** (`--marine`) — единственный «рабочий» акцент:
  активные кнопки, состояние «в сети», активные пункты тулбара.
- **Латунь** (`--brass`) — редкий второстепенный акцент (цитаты, заметки),
  как цвет пера.
- **«Цвета пера»** (`--pen-1…6`) — фиксированная палитра из 6 приглушённых
  тонов для курсоров и аватаров соавторов: каждому участнику достаётся свой
  цвет по кругу, вместо случайного «радужного» набора.
- Типографика: **Fraunces** для заголовков интерфейса/бренда, **Source Serif 4**
  для текста самого документа (документ должен читаться как документ, а не
  как UI), **Public Sans** для элементов управления.

## Частые проблемы при установке

- **`npm install` в `server/` пытается собрать нативный модуль и просит
  Visual Studio / Xcode** — значит используется старая версия этого README
  или Node.js ниже 22.5. Обновите Node.js до 22.5+ (проект больше не зависит
  от `better-sqlite3`, только от встроенного `node:sqlite`) и повторите
  `npm install`.
- **`Cannot find module 'node:sqlite'` или похожая ошибка** — версия Node.js
  ниже 22.5. Проверьте `node -v` и обновите Node (например, через
  [nvm-windows](https://github.com/coreybutler/nvm-windows) или официальный
  установщик с [nodejs.org](https://nodejs.org)).

## Что реализовано сверх обязательного минимума

- **Оглавление документа** — боковая панель в редакторе, автоматически
  собирает все заголовки (H1–H3) и позволяет перейти к любому из них одним
  кликом; обновляется в реальном времени по мере редактирования.
- **Расширенное форматирование** — цвет текста и маркер (ограниченная,
  подобранная под дизайн-систему палитра, а не произвольный color-picker),
  выравнивание абзаца, список задач с чекбоксами, изображения по ссылке,
  увеличение/уменьшение отступа для списков, очистка форматирования.
- **Сетка документов с превью** — на главной странице каждая карточка
  показывает не только название, но и первые строки содержимого (сервер
  извлекает их прямо из сохранённого Yjs-состояния, см.
  `getPreviewText` в `server/src/db/persistence.js`), плюс меню действий
  (переименовать / открыть в новой вкладке / удалить).

## Известные ограничения

- Аутентификации нет — личность (имя + цвет) хранится в `localStorage`
  браузера; для реального продакшена нужен полноценный логин и права доступа
  на документ.
- CORS на сервере открыт (`cors()` без опций) — для продакшена стоит
  ограничить списком разрешённых доменов.
- Список документов кэшируется в `localStorage` для отображения офлайн, но
  создание нового документа в офлайне создаёт локальный черновик
  (`local-<id>`), который зарегистрируется на сервере при первом успешном
  WebSocket-подключении — сам список при этом обновится только после
  восстановления сети.
